## Spec 2: Data Transformation Pipeline
This spec's main feature consists of a data transformation pipeline using dbt on an ECS Task + Athena for querying the S3 parquet files of raw data.
Ideally the feature generation should be thoroguhly decided after a careful EDA. Though for demonstration purposes this step will be ignored though can be revisited. 
The main objective here is to include features that might be relatively simple to compute (cumulative ratio of positive/negative reviews for a game, 
normalizing game developers / publishers list / genres / categories, etc. ) on a cleaned dataset (the scraped data is actually messy, mostly in duplicates and missing data)
and model the main source of truth for training a two tower model.
Three layers: staging, intermediate and marts (following dbt convention)
### Staging:
- Fetch only necessary columns from raw scraped data, with the appropriate data format
- Necessary fields for training the two tower model: `game_id (appid)`, `game_name (name)`, `game_is_free (is_free)`, 
`game_developers`, `game_publishers`, `game_genres`, `game_categories`, `game_review_score`

### Intermediate:
- Deduplicate games by game name, keeping the game id with the highest game review score (simple heuristic found by examining the actual data beforehand),
- Deduplicate reviews by review id (scraping might throw duplicates)

### Marts
- Actual feature engineering, keep a lookup table for game developers, game publishers, game genres, game categories for future embedding table. 
- Compute ratio of positive to negative reviews in an ASOF manner (ratio of positive to negative at the time of review)
- features to compute:
    * users table: `user_id`, `timestamp`, `games_reviewed_positive` (list of a maximum of 5 games padded with 0 if not more than 5 at current moment)
    * games table: `game_id`, `timestamp`, `game_name`, `game_is_free`, `game_developers`, `game_publishers`, `game_genres`, `game_categories`, `game_reviews_ratio`, `game_review_score`
    * interactions: `review_id`, `timestamp`, `user_id`, `game_id`, **user_features, **game_features
The interactions table, as probably inferred, needs to be generated by an asof join since user and item features change over time.

Additional considerations:
- Pipeline must be incremenal and idempotent. Meaning running the pipeline after an initial backfill should land only the newest reviews and games, as well as 
ID's (devs, publishers, etc.) on the Iceberg Tables.
- Analyze for the size of the dataset should the ID's conversion to incremental integers (for faster usage in embeddings table) should happen at the data transformation layer 
or be stored as a training artifact.
